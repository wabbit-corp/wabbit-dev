Why Good Commit Messages Matter
-------------------------------

High-quality commit messages are more than a courtesy – they directly impact software maintainability. Empirical studies have shown that detailed commit messages correlate with better code quality. For example, one study found that adding commit message length and informative content as factors significantly improved models for predicting defect-prone commits[rebels.cs.uwaterloo.ca](https://rebels.cs.uwaterloo.ca/papers/msr2016_barnett.pdf#:~:text=dataset%20,power%20of%20our%20JIT%20models)[rebels.cs.uwaterloo.ca](https://rebels.cs.uwaterloo.ca/papers/msr2016_barnett.pdf#:~:text=,power%20of%20our%20JIT%20models). In practice, **commits with poor or absent messages can impede understanding**, leading developers to misinterpret changes and potentially introduce new bugs later[github.blog](https://github.blog/developer-skills/github/write-better-commits-build-better-projects/#:~:text=Even%20with%20a%20clear%20narrative,of%20the%20code%20you%E2%80%99ve%20changed). Conversely, descriptive messages (explaining _what_ changed and _why_) help future maintainers grasp the intent of changes, reducing technical debt and errors[stairs.ics.uci.edu](https://stairs.ics.uci.edu/papers/2023/Commit_Messages.pdf#:~:text=messages%20and%20technical%20debt,these%20studies%20only%20considered%20syntactic)[github.blog](https://github.blog/developer-skills/github/write-better-commits-build-better-projects/#:~:text=Even%20in%20a%20best,wasting%20everyone%E2%80%99s%20time%20and%20energy). Both research and industry experts agree that commit messages serve as an important communication tool: they provide context beyond the code diff, acting as a historical record of decisions and rationales[stairs.ics.uci.edu](https://stairs.ics.uci.edu/papers/2023/Commit_Messages.pdf#:~:text=among%20OSS%20developers%2C%20in%20the,specifically%20investigating%20the%20impact%20of)[github.blog](https://github.blog/developer-skills/github/write-better-commits-build-better-projects/#:~:text=Commits%20are%20more%20than%20just,change%20in%20your%20own%20terms). In short, writing clear commit messages is a simple practice that pays off in easier code reviews, debugging, and onboarding to a project.

Standard Conventions for Commit Message Format
----------------------------------------------

Over decades of use, the software community has converged on a set of conventions that make commit histories cleaner and more readable. These guidelines are recommended in academic literature and by leading engineering teams (Google’s style guide, for instance, endorses them[google.github.io](https://google.github.io/styleguide/#:~:text=Since%20projects%20are%20largely%20maintained,trivial%20to%20translate%20to%20others)). The most common conventions include the following:

*   **Write a concise subject line** – Ideally **50 characters or less**, starting with a capital letter and **no period** at the end[theserverside.com](https://www.theserverside.com/video/Follow-these-git-commit-message-guidelines#:~:text=,and%20why%2C%20but%20not%20how). This summary line is crucial: many tools show only the first line, so it should capture the essence of the change.
    
*   **Separate the subject from the body with a blank line**[theserverside.com](https://www.theserverside.com/video/Follow-these-git-commit-message-guidelines#:~:text=,Use%20the%20imperative%20mood). The blank line ensures tools like `git log` or email alerts recognize the subject and body correctly.
    
*   **Limit the line length in the body** to around **72 characters** for readability in terminals and other tools[theserverside.com](https://www.theserverside.com/video/Follow-these-git-commit-message-guidelines#:~:text=,Use%20the%20imperative%20mood). Wrapping text prevents it from overflowing on an 80-character terminal display[tbaggery.com](https://tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html#:~:text=Capitalized%2C%20short%20,summary).
    
*   **Use the imperative mood** in the subject (and in any bullet points)[theserverside.com](https://www.theserverside.com/video/Follow-these-git-commit-message-guidelines#:~:text=,and%20why%2C%20but%20not%20how). In other words, write as if giving a command: **“Fix typo in login flow”** instead of “Fixed typo” or “Fixing typo.” This style (“If applied, this commit will _fix typo…_”) is widely adopted and matches automatically generated messages from commands like Git merge[tbaggery.com](https://tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html#:~:text=Write%20your%20commit%20message%20in,git%20merge%20and%20git%20revert).
    
*   **Describe _what_ the commit does and **why**, not how**[theserverside.com](https://www.theserverside.com/video/Follow-these-git-commit-message-guidelines#:~:text=,and%20why%2C%20but%20not%20how). The code diff itself shows how the change was made; the commit message should summarize the intent and reasoning. For example, **“Add caching to improve response time”** is more useful than “modify `cache.py`.” If the commit fixes a bug or adds a feature, state the problem or goal and the motivation for the change.
    

These formatting rules (often called the “50/72 rule” and related guidelines) are considered best practice across many organizations[theserverside.com](https://www.theserverside.com/video/Follow-these-git-commit-message-guidelines#:~:text=The%20seven%20commonly%20accepted%20git,best%20practices%20are%20as%20follows). Following a consistent structure makes it easier for anyone reading the history – whether a teammate or an open-source contributor – to quickly scan commit logs. Many open-source projects (Linux, OpenStack, Angular, etc.) and companies have published similar rules for commit messages, underlining their universal value.

Writing Informative and Clear Commit Messages
---------------------------------------------

Beyond the basic format, the content of a commit message should give enough context to make the change understandable on its own. A good commit message **explains the **“why”** behind the change**. As one developer advice puts it: _“first and foremost add context (the why, not the how) with your commit message”_[stackoverflow.com](https://stackoverflow.com/questions/15324900/standard-to-follow-when-writing-git-commit-messages#:~:text=Therefore%2C%20first%20and%20foremost%20add,is%20worth%20so%20much%20more). In practice, this means the commit message should include any background needed to understand the change:

*   **Briefly state the problem or feature being addressed.** For a bug fix, mention the issue or unexpected behavior that prompted the change. For a new feature or improvement, state the goal. This provides readers with the _context_ behind the code changes[wiki.openstack.org](https://wiki.openstack.org/wiki/GitCommitMessages#Information_in_commit_messages#:~:text=,what%20the%20original%20problem%20was)[wiki.openstack.org](https://wiki.openstack.org/wiki/GitCommitMessages#Information_in_commit_messages#:~:text=,documenting).
    
*   **Explain the rationale (why the change is necessary).** For example: “Improve caching to reduce page load times” or “Fix race condition causing intermittent crashes.” This helps reviewers and future maintainers follow your reasoning[github.blog](https://github.blog/developer-skills/github/write-better-commits-build-better-projects/#:~:text=). If the reasoning is tied to an external discussion (issue tracker, support ticket), summarize the key points in the commit message so it stands on its own.
    
*   **Avoid simply restating code diff or function names.** Don’t write messages like “Update `utils.py`” or “Change X to Y” without context. Instead, describe the outcome or intent: _what functionality is added or what bug is fixed_. Remember that **the code change itself shows the “how”; your message should highlight the “what” and “why.”** This guidance is echoed in both community forums and formal style guides[stairs.ics.uci.edu](https://stairs.ics.uci.edu/papers/2023/Commit_Messages.pdf#:~:text=More%20recently%2C%20Tian%20et%20al,In%20our)[wiki.openstack.org](https://wiki.openstack.org/wiki/GitCommitMessages#Information_in_commit_messages#:~:text=,is%20being%20made).
    
*   **Make the message self-contained.** Future developers (or your future self) might read the commit history without access to external systems. A classic guideline is that someone reviewing offline (or years later) should understand a commit without needing to hunt down a Jira ticket or GitHub issue[wiki.openstack.org](https://wiki.openstack.org/wiki/GitCommitMessages#Information_in_commit_messages#:~:text=,access%20to%20external%20web%20services%2Fsite). Therefore, if you reference an issue ID or link, also include a brief description of the issue’s nature or resolution. For instance: _“Fix memory leak in image processing (Issue #1234)”_ gives context, whereas just writing _“Issue #1234 resolved”_ would force the reader to look up the issue.
    
*   **Reference relevant IDs or links in the footer when applicable.** It’s often helpful (especially in corporate or open-source projects) to include references to bug trackers, issue numbers, or external discussions. Many teams use a **“footer”** section for this purpose. For example, you might add lines like **“Resolves: #123”** or **“Fixes JIRA-456”** at the end of the message[dev.to](https://dev.to/chrissiemhrk/git-commit-message-5e21#:~:text=,789). This ties the commit to broader tracking systems, enabling auto-closing of issues and traceability. Just ensure that, as noted above, you also summarize the issue in the commit message so it’s understandable without needing to click the link.
    
*   **Indicate scope or component (if relevant).** In large projects, it’s helpful to mention the subsystem or module affected by the commit in the subject line. Many projects prefix commit summaries with a tag or component name (for example, **“database: Improve indexing for user table”**). This practice is reflected in conventions like **Conventional Commits**, where the “type” or a scope is included in the title. It helps readers know at a glance which part of the codebase is changed[wiki.openstack.org](https://wiki.openstack.org/wiki/GitCommitMessages#Information_in_commit_messages#:~:text=,is%20the%20most%20important). For instance, a commit in a web project might start with **“frontend:”**, **“backend:”**, or **“docs:”** to categorize the change.
    

Additionally, writing a good commit message starts with **crafting a good commit**. It’s much easier to describe a focused, single-purpose change than one that mixes many unrelated modifications. As a best practice, **keep commits small and atomic** – each commit should accomplish one distinct task or fix one issue[microsoft.github.io](https://microsoft.github.io/code-with-engineering-playbook/source-control/git-guidance/#:~:text=,commit%20incomplete%20code%2C%20get%20in). This way your commit message can clearly describe that change. If you find yourself struggling to summarize a commit, it might be a sign that the commit should be split into multiple commits (each with its own message)[wiki.openstack.org](https://wiki.openstack.org/wiki/GitCommitMessages#Information_in_commit_messages#:~:text=,hints%20at%20improved%20code%20structure).

Examples of Well-Written Commit Messages
----------------------------------------

To illustrate, consider a few examples that reflect these guidelines. One emerging standard is the **Conventional Commits** format (adopted in many open-source projects and tools). It adds a structured prefix to the commit title indicating the type of change:

> **Example:** `chore: Upgrade library XYZ to version 1.2.3`  
> This commit’s body would then explain the reason: _“Upgrade resolves security vulnerability CVE-2021-\_\_\_\_. Unpatched, the flaw could allow attackers to bypass authentication in the payment workflow.”_[stackoverflow.com](https://stackoverflow.com/questions/70362399/some-references-including-examples-for-good-git-commit-messages#:~:text=With%20this%20convention%2C%20upgrading%20a,e.g)

In the above example, the **subject** follows a clear pattern: a type (`chore`) and a short summary of _what_ was done (“Upgrade library XYZ to version 1.2.3”). The **body** provides the context – the “why” – explaining that this upgrade fixes a known security issue. Anyone reviewing the history can immediately see what the commit is about and understand its importance without needing to read the code diff or external advisories. Many teams use similar structures (e.g. types like **feat**, **fix**, **refactor**, etc.) to consistently label commits[stackoverflow.com](https://stackoverflow.com/questions/70362399/some-references-including-examples-for-good-git-commit-messages#:~:text=There%20isn%27t%20a%20definitive%20standard,it%20would%20be%20Conventional%20Commits), which can also be leveraged by automation (for generating changelogs or determining version bumps).

As another example, imagine a commit that fixes a bug in a form validation module:

**Bad:** `Fixed stuff` – (Too vague, no indication of scope or reason.)  
**Good:** `fix(form-validation): handle empty email address` – (Clearly states what is fixed and where.)  
_Body:_ “Previously, submitting the form with an empty email caused a null-pointer exception. This fix adds a check to prevent that. **Why**: Ensures a smoother user experience by preventing a crash on form submit for missing email.”

In the good message above, the subject identifies the area (_form-validation_) and the nature of the fix. The body provides both the _what_ (added a check) and the _why_ (to prevent a crash and improve UX). A reviewer or future developer can quickly recall the issue this commit addressed.

These examples highlight a common structure for effective commit messages:

1.  **Title/Subject:** A one-line summary _in imperative mood_, possibly prefixed with a category or component.
    
2.  **Body (optional):** Explanation of the change – **why it was made, what problem it solves or what benefit it brings**. Include any crucial details that aren’t obvious from reading the code diff. Keep the tone factual and concise, and line-wrap for readability.
    
3.  **Footer (optional):** References to issue numbers, PRs, or co-authors (if needed). This can include phrases like “Closes #issue” to auto-link or close tickets.
    

Best Practices from Industry and Communities
--------------------------------------------

The above guidelines aren’t just theoretical – they’ve been affirmed by both community consensus and industry standards:

*   **Open Source Communities:** Projects like OpenStack and the Linux kernel have documented commit message conventions that align with these principles. OpenStack’s guide, for instance, emphasizes not assuming the reader knows the bug or the code – the commit message should _stand alone_ in explaining the change[wiki.openstack.org](https://wiki.openstack.org/wiki/GitCommitMessages#Information_in_commit_messages#:~:text=,access%20to%20external%20web%20services%2Fsite)[wiki.openstack.org](https://wiki.openstack.org/wiki/GitCommitMessages#Information_in_commit_messages#:~:text=,documenting). It also stresses the importance of the first line and encourages mentioning the affected component in that line[wiki.openstack.org](https://wiki.openstack.org/wiki/GitCommitMessages#Information_in_commit_messages#:~:text=,is%20the%20most%20important). Such projects often require commit messages to pass certain checks before contributions are accepted, underlining their importance in collaborative development.
    
*   **Corporate Environments:** Companies like **Google** and **Microsoft** train developers in these best practices. Google’s engineering guidelines explicitly reference the well-known “How to Write a Git Commit Message” guide[google.github.io](https://google.github.io/styleguide/#:~:text=Since%20projects%20are%20largely%20maintained,trivial%20to%20translate%20to%20others), and many Google-originated projects (e.g. Angular) use the Conventional Commits style to keep commit history clean. Microsoft’s engineering playbook advises writing descriptive messages covering the necessity and effects of a change[microsoft.github.io](https://microsoft.github.io/code-with-engineering-playbook/source-control/git-guidance/#:~:text=,include%20benchmarks%2C%20side%20effects%20etc), and keeping commits small to facilitate clear messaging[microsoft.github.io](https://microsoft.github.io/code-with-engineering-playbook/source-control/git-guidance/#:~:text=,commit%20incomplete%20code%2C%20get%20in). Across big tech firms, it’s common to link commits to work items (Jira, Azure DevOps, etc.), and the expectation is that the commit message provides a human-readable summary beyond just an ID.
    
*   **Developer Communities:** On forums like Stack Overflow, experienced developers frequently underscore the value of good commit messages. A highly-voted answer notes that a commit message should _“communicate the essence of the change”_ and especially highlight the **why** – something the code itself doesn’t convey[stackoverflow.com](https://stackoverflow.com/questions/15324900/standard-to-follow-when-writing-git-commit-messages#:~:text=Therefore%2C%20first%20and%20foremost%20add,is%20worth%20so%20much%20more). Developers share tips like imagining what message would help them if they encountered this change months later or when digging through history, and almost universally point to the same core rules (subject length, imperative mood, etc.) as outlined above.
    

By following these best practices, you can write commit messages that are informative, professional, and useful across diverse development environments. In summary, **treat the commit message as an integral part of the change** – it should **tell the story of the code**. A commit with a well-written message is easier to review and far more valuable to the team (and to your future self) than one with an ambiguous or empty message. Whether you’re working in a large open-source project or a small corporate team, the same principles apply: **be concise, be clear, and provide context**. Adopting these habits will lead to a more maintainable codebase and a version control history that truly documents the evolution of the software[github.blog](https://github.blog/developer-skills/github/write-better-commits-build-better-projects/#:~:text=).
