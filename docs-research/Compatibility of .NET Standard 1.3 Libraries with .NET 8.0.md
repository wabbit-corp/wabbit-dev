General Support in .NET 8 for .NET Standard 1.3
-----------------------------------------------

**Full Backward Compatibility:** .NET 8 (like .NET 5, 6, and 7 before it) is designed to **fully support .NET Standard 2.1 and all earlier .NET Standard versions**, including .NET Standard 1.3[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=For%20existing%20code%20that%20targets,5%20or%20a%20later%20version). This means a library targeting .NET Standard 1.3 can be referenced by a .NET 8 project and should run without modification. In other words, .NET 8 implements the entire API surface defined by .NET Standard 1.3 (and more), ensuring that existing binaries targeting .NET Standard 1.3 _“will work forever”_ on new .NET runtimes[learn.microsoft.com](https://learn.microsoft.com/en-us/answers/questions/628118/will-net-standard-support-net-6#:~:text=According%20to%20this%20document%2C%20,standard). There is no need to recompile or retarget such libraries just to make them **usable** in .NET 8 – they are _binary compatible_ by design.

**No New .NET Standard Version Needed:** Microsoft has indicated that .NET 5+ unifies the platform, so they won’t create new .NET Standard versions. Instead, **.NET 5 and all future versions (including .NET 8) continue to support .NET Standard 2.1 and earlier** as the basis for cross-platform libraries[devblogs.microsoft.com](https://devblogs.microsoft.com/dotnet/the-future-of-net-standard/#:~:text=We%20won%E2%80%99t%20be%20releasing%20a,for%20sharing%20code%20moving%20forward). In practice, a `.NET 8` target framework moniker (TFM) _already includes_ everything from .NET Standard. The only reason you’d ever need to **retarget** a library from .NET Standard 1.3 to .NET 8 is to gain access to newer features or APIs that didn’t exist in .NET Standard 1.3[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=For%20existing%20code%20that%20targets,5%20or%20a%20later%20version). For example, if a library or component wants to use C# 9/10 language features or new runtime APIs, it would need to target a modern .NET TFM like `net8.0` (since .NET Standard 1.3 only supports older C# and a limited API set)[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=change%20the%20TFM%20to%20,5%20or%20a%20later%20version). But for **general usage**, .NET 8 can consume .NET Standard 1.3 libraries directly with no special steps.

Limitations and Compatibility Concerns
--------------------------------------

While .NET 8 can _run_ .NET Standard 1.3 libraries, there are some limitations and considerations when using these older libraries:

*   **Limited API Surface:** .NET Standard 1.3 is an older specification and only includes a subset of the APIs available in modern .NET. In fact, .NET Standard 1.3 exposed roughly 13k APIs, which is far smaller than the full .NET 8 BCL (by comparison, .NET Standard 2.0+ covers ~32k APIs)[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=,of%20the%2037%2C118%20available%20APIs). This means a library targeting 1.3 may be **missing newer functionality** or convenience APIs. The library will run, but it might rely on more basic implementations because it couldn’t use later APIs introduced after .NET Standard 1.3. Developers integrating such a library should be aware that its functionality might be somewhat constrained by what .NET Standard 1.3 offered.
    
*   **Granular NuGet Dependencies:** The .NET Standard 1.x era (including 1.3) shipped as a collection of many small NuGet packages (for example, `System.Runtime`, `System.Linq`, etc. as separate packages) rather than one unified platform. If you have a .NET Standard 1.3 class library, it may list numerous NuGet package dependencies. On .NET 8, these resolve to the built-in base class library, so you typically won’t need to manually add anything – but the _build process_ could pull in a large graph of compatibility packages if not handled by the SDK. Microsoft notes that **.NET Standard 1.x results in a “large package dependency graph”** and many packages downloaded, since it was so granular[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/9.0/netstandard-warning#:~:text=The%20build%20warning%20was%20introduced,when%20the%20project%20is%20built). This is more of a build/package management concern than a runtime problem (because .NET 8 includes those APIs internally), but it’s a reason .NET Standard 1.x is seen as somewhat _cumbersome_ by today’s standards.
    
*   **Obsolete or Changed APIs:** Even though .NET 8 implements all .NET Standard 1.3 APIs, some of those APIs have been _deprecated or changed_ in behavior over time. An older library might call an API that still exists in .NET 8 but is now marked **\[Obsolete\]** or has altered semantics. For example, certain cryptography methods that existed in .NET Standard (such as `RSA.EncryptValue`/`DecryptValue`) are **obsolete in .NET 8** and were removed from the public API surface[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/8.0#:~:text=RSA,incompatible%20Preview%201). If a .NET Standard 1.3 library happens to use such APIs, it could encounter build warnings or runtime differences on .NET 8. (In the RSA case, the methods would simply no longer be available when recompiling against .NET 8; existing binaries might continue to run since those were rarely used low-level methods.) Another example is the old `System.Net.WebRequest` API – which is included in .NET Standard and still present in .NET 8 for compatibility, but it’s deprecated and may not behave exactly as on .NET Framework (it’s recommended to use `HttpClient` instead). These edge cases are _rare_, but developers should be mindful of any warnings that appear when referencing the library, as they may highlight usage of APIs that .NET 8 considers legacy.
    
*   **Behavioral Differences:** Even without outright deprecations, .NET 8 has introduced some **behavioral changes** in the base libraries that could subtly affect older code. These are generally corner cases, but worth noting. For instance, .NET 8 changed how certain file paths are normalized on Unix (mapping of backslashes) and how Base64 decoding handles whitespace[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/8.0#:~:text=Activity%20operation%20name%20when%20null,change%20%2024%20Behavioral%20change). A .NET Standard 1.3 library doing file I/O or parsing might observe slightly different behavior under the hood on .NET 8 compared to older runtimes. Such changes are usually fixes or improvements, but they could represent a **minor compatibility issue** if the library assumed the older behavior. It’s a good idea to run the library’s functionality under .NET 8 in a test environment to catch any surprises (e.g. differences in exception types, stricter validation, etc., that have evolved over .NET Core releases).
    
*   **Platform-Specific Gaps:** By design, .NET Standard 1.3 avoids platform-specific APIs (no Windows-only libraries like WPF, no web server APIs, etc.), so you generally won’t run into “platform not supported” issues as long as the library stayed within the standard. One notable gap: some frameworks or libraries that were optional even in .NET Standard (available via separate packages) might not be fully supported in .NET 8. For example, **System.DirectoryServices** was not originally in .NET Standard 1.3, and while later made available as a NuGet package, on .NET 8 this area is not supported on non-Windows platforms (and is out of support altogether)[stackoverflow.com](https://stackoverflow.com/questions/37330705/working-with-directoryservices-in-asp-net-core#:~:text=). If your .NET Standard library tried to use something like DirectoryServices or other older enterprise-oriented APIs, you might need an updated approach on .NET 8. In general though, pure .NET Standard 1.3 libraries stick to the common denominator APIs, which .NET 8 supports cross-platform.
    

**Key Point:** There are _no fundamental blockers_ to using a .NET Standard 1.3 library in .NET 8 – it should _work out of the box_. The “limitations” are mostly that the library is confined to an older API set and might not take advantage of improvements since then. Also, as .NET evolves, Microsoft is encouraging moving away from those older targets. In fact, starting with the .NET 9 SDK, building a project that targets .NET Standard 1.x will emit a warning (NETSDK1215) to alert you that _“Targeting .NET Standard prior to 2.0 is no longer recommended.”_[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/9.0/netstandard-warning#:~:text=Starting%20in%20,the%20following%20warning%20is%20emitted)[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/9.0/netstandard-warning#:~:text=The%20build%20warning%20was%20introduced,when%20the%20project%20is%20built). This doesn’t break anything in .NET 8; it’s just guidance that you’re using an outdated target.

Best Practices for Using .NET Standard 1.3 Libraries in .NET 8
--------------------------------------------------------------

If you find yourself working with a .NET Standard 1.3 library in a .NET 8 project, consider the following best practices and recommendations:

*   **Prefer Newer Targets for New Development:** If **you maintain** the library’s code (or have the ability to fork/rebuild it), strongly consider upgrading its target. Microsoft _recommends retargeting .NET Standard 1.x libraries to .NET Standard 2.0 or directly to a modern .NET version (like net8.0)_[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20your%20project%20targets%20,x%20targets). Targeting .NET Standard 2.0 is often a safe bet because it dramatically expands the available API surface while still supporting older platforms (including .NET Framework 4.6.1+)[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20you%27re%20building%20reusable%20libraries,a%20minimal%20increase%20in%20reach). In many cases, jumping all the way to a **.NET 8** target can be ideal if you no longer need to support anything older than .NET 8 – this lets you use the latest runtime features and C# versions in the library. The general guidance is: _“We don't recommend targeting .NET Standard 1.x, as you'd limit the available feature set for a minimal increase in reach.”_[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20you%27re%20building%20reusable%20libraries,a%20minimal%20increase%20in%20reach). So for any actively developed library, move it forward if possible.
    
*   **Multi-Target for Broad Compatibility:** If you need to maintain broad compatibility (for example, your library is used in some .NET Framework 4.x projects as well as .NET 8), you can **multi-target** the project. Many NuGet packages choose to target both **`netstandard2.0`** (to cover .NET Framework and older .NET Core) and **`net5.0`/`net6.0`+** (to light up new features) in one package. Microsoft notes that most widely-used libraries do exactly this: _support .NET Standard 2.0 for maximal reach, and add a .NET 5+ target to leverage latest features on newer runtimes_[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20you%20don%27t%20need%20to,NET%205). You could similarly multi-target `netstandard1.3` and `net8.0`, but since .NET Standard 2.0 supersedes 1.3 with almost the same reach, it’s usually better to target 2.0 instead of 1.3 for the “common denominator” target. In summary, consider delivering an updated version of the library that at least targets .NET Standard 2.0 (if not higher) alongside your .NET 8 code. This way, your .NET 8 project can take a dependency on a more up-to-date library build (eliminating the need for all those 1.x compatibility shims and giving you more API to work with internally).
    
*   **Check for Upgraded Versions:** If the .NET Standard 1.3 library is a third-party or legacy NuGet package that you consume, search to see if a newer version of that library exists. Many projects that started on .NET Standard 1.x have released updates targeting .NET Standard 2.0 or .NET 6/7/8 as the ecosystem evolved. Upgrading to a later version of the package can resolve compatibility quirks and improve performance. It can also get rid of any build warnings about older targets. For example, some libraries initially targeting .NET Standard 1.3 (for maximum reach at the time) later added .NET 6/7 support once those became widely adopted (often indicated on NuGet as “netstandard1.3; net6.0; net7.0” targets, etc.)[github.com](https://github.com/GregFinzer/Compare-Net-Objects/blob/master/Readme.md#:~:text=NET%20Framework%204,Android)[nuget.org](https://www.nuget.org/packages/comparenetobjects/#:~:text=,4). Always prefer the latest compatible version of a library for a .NET 8 project, as it’s likely been tested with .NET Core/5+ environments.
    
*   **Test the Integrated Library:** After adding the .NET Standard 1.3 library to your .NET 8 project, **run your tests** or exercise the library’s functionality thoroughly. Although no compile-time issues are expected, runtime testing can reveal any subtle differences (for example, maybe the library performs reflection or file access that behaves differently on .NET 8, etc.). Pay attention to any console or log warnings that .NET might emit about deprecated APIs when the app runs. In general, if the library is purely computation or business logic, it should behave the same. But if it deals with resource loading, configuration, or other runtime interactions, validate those in the new environment.
    
*   **Monitor .NET 8 Specific Warnings/Errors:** If you compile the library from source against .NET 8 (or if your solution includes the library project targeting net8.0), you might encounter **compiler warnings** for outdated patterns. For instance, async code may show analyzers suggestions, or using certain older .NET idioms might trigger warnings under the latest SDK. Addressing these (if you have access to the code) can make the library more robust. Even if you’re just consuming a binary, Visual Studio may show you an analyzer warning if the library uses something like `BinaryFormatter` or other deprecated component – these are cues to be aware of potential issues. (For example, if a .NET Standard 1.3 library internally uses an API that’s obsolete, you might see an MSBuild warning or runtime advisory about it.)
    
*   **Maintain a Unified Target Platform if Possible:** When developing your application, it’s simpler if all projects use modern targets. If you have the option to update the class library (or find an updated fork), doing so will let you keep your entire solution on a uniform, supported target (e.g., everything on .NET 8). This avoids the mental overhead of mixing old and new targets. However, if the .NET Standard 1.3 library is from a third party and cannot be changed, rest assured that referencing it is supported. Just consider isolating it if needed, and plan long-term to replace or update it if the opportunity arises (since .NET Standard 1.x is essentially _frozen_ and not recommended for new work[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20you%27re%20building%20reusable%20libraries,a%20minimal%20increase%20in%20reach)).
    

Specific API Considerations in .NET 8
-------------------------------------

Most of the APIs in .NET Standard 1.3 are basic functionalities that continue to work in .NET 8. However, it’s worth highlighting a few **specific APIs/patterns** that could pose issues or deserve attention:

*   **BinaryFormatter and Legacy Serialization:** Although .NET Standard 1.3 itself did _not_ include `BinaryFormatter` (it was added in .NET Standard 2.0), some older libraries might use binary serialization or similar techniques via conditional compilation. In .NET 8, `BinaryFormatter` is **fully obsolete and even disabled** in many scenarios due to security concerns. For example, a developer reported that a .NET Standard library using BinaryFormatter ran into runtime exceptions on .NET 8 – the app crashed on .NET 8 because _“the binary formatter serialization and deserialization are disabled”_ by default for security[stackoverflow.com](https://stackoverflow.com/questions/78267859/does-net-8-really-support-net-standard-2-0-binaryformatter-issue#:~:text=I%20also%20have%20an%20app,8.0). This illustrates that **support doesn’t always mean identical behavior**: .NET 8 _includes_ the BinaryFormatter API for compatibility (fulfilling .NET Standard 2.0), but actually using it will trigger errors unless explicitly re-enabled. **Recommendation:** If an older library uses `BinaryFormatter` or similar deprecated serialization, you should update that part of the code (e.g., switch to `System.Text.Json` or `XmlSerializer`) or ensure the feature is turned off, because .NET 7/8 actively blocks BinaryFormatter usage by default[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/serialization/5.0/binaryformatter-serialization-obsolete#:~:text=Due%20to%20security%20vulnerabilities%20,enabled%20%203%20functionality).
    
*   **Cryptography APIs:** As mentioned, certain crypto primitives from early .NET are present but deprecated. .NET 8 marked the old `RSA.EncryptValue` and `RSA.DecryptValue` methods as obsolete (and they were removed from the public contract in .NET 7+)[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/8.0#:~:text=RSA,incompatible%20Preview%201). These methods aren’t commonly used (they were low-level hooks usually not needed with RSA), but if a .NET Standard 1.3 library somehow relies on them, it would not compile against .NET 8 and could fail at runtime if it tries to invoke them via reflection. The broader RSA API and other cryptography functions (like SHA hashing, AES, etc.) continue to work, but developers should use the newer recommended patterns. Similarly, older SSL/TLS configurations or algorithms considered insecure may be disabled by default in .NET 8’s networking stack. If your library dealt with things like TLS 1.0/1.1, be aware that .NET 8 (and even 6/7) may require TLS 1.2+ by default in many contexts.
    
*   **Networking and HTTP:** .NET Standard 1.3 libraries might use `HttpClient` (which is fully supported in .NET 8) or possibly `WebRequest/WebClient`. The latter (WebRequest) is deprecated in .NET 6+; it’s still functional, but on .NET 8 it will log warnings that it’s not the recommended API. Functionally, a library using WebRequest should still work (the compatibility shims are there), but performance may not be optimal. If you maintain the lib, port it to HttpClient for better support. If you just use it, there’s no breaking issue – just something to note if you see deprecation messages.
    
*   **Threading and Sync Context:** .NET Standard 1.3 supports basic threading/tasks, and those behave the same in .NET 8. One change in .NET 8 (and .NET 6) is improvements to the thread pool and synchronization contexts, but that should _improve_ performance or deadlock avoidance for libraries using `Task` and `async/await`. No action needed, but if your library had custom Task scheduling, just be aware of any subtle differences.
    
*   **Reflection and Emission:** Most reflection APIs from .NET Standard 1.3 (Type inspection, MethodInfo.Invoke, etc.) are fully available. .NET 8 does have the “trimming” and ahead-of-time compile features which can affect reflection (e.g., if you publish with trimming, reflection heavy libraries might need extra config). But in a normal .NET 8 app, reflection works as usual. If the library uses `Assembly.Load(byte[])` or dynamic code gen (`System.Reflection.Emit`), those are also supported on core (with the exception of some contexts like Native AOT). There’s no outright removal here, but something to keep in mind if deploying to an AOT scenario.
    
*   **Platform Invokes (P/Invoke):** If the .NET Standard 1.3 library uses P/Invoke to call native code, it should still work on .NET 8 _provided_ the native dependency is available. .NET 8’s interop is compatible with how .NET Core has always done it. Just ensure any native libraries are present for the OS you run on (Windows vs Linux, etc.). Nothing specific in .NET 8 breaks P/Invokes from .NET Standard libs.
    

In summary, **nearly all APIs from .NET Standard 1.3 function correctly in .NET 8**, but you should be alert to those that .NET 8 has marked as obsolete or changed for security/performance. Reading through the _.NET 8 breaking changes_ documentation (especially for core libraries) can be useful if your older library does something unusual. The good news is that common functionality (collections, LINQ, IO, networking, threading, etc.) was carried forward with full compatibility. The .NET team has been careful to keep the promise that “if it was in .NET Standard, it’ll continue to exist in .NET 5+” – with only a few exceptions where they _soft-removed_ things by obsoleting them.

Developers integrating such a library should be aware that its functionality might be somewhat constrained by what .NET Standard 1.3 offered.
    
*   **Granular NuGet Dependencies:** The .NET Standard 1.x era (including 1.3) shipped as a collection of many small NuGet packages (for example, `System.Runtime`, `System.Linq`, etc. as separate packages) rather than one unified platform. If you have a .NET Standard 1.3 class library, it may list numerous NuGet package dependencies. On .NET 8, these resolve to the built-in base class library, so you typically won’t need to manually add anything – but the _build process_ could pull in a large graph of compatibility packages if not handled by the SDK. Microsoft notes that **.NET Standard 1.x results in a “large package dependency graph”** and many packages downloaded, since it was so granular[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/9.0/netstandard-warning#:~:text=The%20build%20warning%20was%20introduced,when%20the%20project%20is%20built). This is more of a build/package management concern than a runtime problem (because .NET 8 includes those APIs internally), but it’s a reason .NET Standard 1.x is seen as somewhat _cumbersome_ by today’s standards.
    
*   **Obsolete or Changed APIs:** Even though .NET 8 implements all .NET Standard 1.3 APIs, some of those APIs have been _deprecated or changed_ in behavior over time. An older library might call an API that still exists in .NET 8 but is now marked **\[Obsolete\]** or has altered semantics. For example, certain cryptography methods that existed in .NET Standard (such as `RSA.EncryptValue`/`DecryptValue`) are **obsolete in .NET 8** and were removed from the public API surface[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/8.0#:~:text=RSA,incompatible%20Preview%201). If a .NET Standard 1.3 library happens to use such APIs, it could encounter build warnings or runtime differences on .NET 8. (In the RSA case, the methods would simply no longer be available when recompiling against .NET 8; existing binaries might continue to run since those were rarely used low-level methods.) Another example is the old `System.Net.WebRequest` API – which is included in .NET Standard and still present in .NET 8 for compatibility, but it’s deprecated and may not behave exactly as on .NET Framework (it’s recommended to use `HttpClient` instead). These edge cases are _rare_, but developers should be mindful of any warnings that appear when referencing the library, as they may highlight usage of APIs that .NET 8 considers legacy.
    
*   **Behavioral Differences:** Even without outright deprecations, .NET 8 has introduced some **behavioral changes** in the base libraries that could subtly affect older code. These are generally corner cases, but worth noting. For instance, .NET 8 changed how certain file paths are normalized on Unix (mapping of backslashes) and how Base64 decoding handles whitespace[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/8.0#:~:text=Activity%20operation%20name%20when%20null,change%20%2024%20Behavioral%20change). A .NET Standard 1.3 library doing file I/O or parsing might observe slightly different behavior under the hood on .NET 8 compared to older runtimes. Such changes are usually fixes or improvements, but they could represent a **minor compatibility issue** if the library assumed the older behavior. It’s a good idea to run the library’s functionality under .NET 8 in a test environment to catch any surprises (e.g. differences in exception types, stricter validation, etc., that have evolved over .NET Core releases).
    
*   **Platform-Specific Gaps:** By design, .NET Standard 1.3 avoids platform-specific APIs (no Windows-only libraries like WPF, no web server APIs, etc.), so you generally won’t run into “platform not supported” issues as long as the library stayed within the standard. One notable gap: some frameworks or libraries that were optional even in .NET Standard (available via separate packages) might not be fully supported in .NET 8. For example, **System.DirectoryServices** was not originally in .NET Standard 1.3, and while later made available as a NuGet package, on .NET 8 this area is not supported on non-Windows platforms (and is out of support altogether)[stackoverflow.com](https://stackoverflow.com/questions/37330705/working-with-directoryservices-in-asp-net-core#:~:text=). If your .NET Standard library tried to use something like DirectoryServices or other older enterprise-oriented APIs, you might need an updated approach on .NET 8. In general though, pure .NET Standard 1.3 libraries stick to the common denominator APIs, which .NET 8 supports cross-platform.
    

**Key Point:** There are _no fundamental blockers_ to using a .NET Standard 1.3 library in .NET 8 – it should _work out of the box_. The “limitations” are mostly that the library is confined to an older API set and might not take advantage of improvements since then. Also, as .NET evolves, Microsoft is encouraging moving away from those older targets. In fact, starting with the .NET 9 SDK, building a project that targets .NET Standard 1.x will emit a warning (NETSDK1215) to alert you that _“Targeting .NET Standard prior to 2.0 is no longer recommended.”_[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/9.0/netstandard-warning#:~:text=Starting%20in%20,the%20following%20warning%20is%20emitted)[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/9.0/netstandard-warning#:~:text=The%20build%20warning%20was%20introduced,when%20the%20project%20is%20built). This doesn’t break anything in .NET 8; it’s just guidance that you’re using an outdated target.

Best Practices for Using .NET Standard 1.3 Libraries in .NET 8
--------------------------------------------------------------

If you find yourself working with a .NET Standard 1.3 library in a .NET 8 project, consider the following best practices and recommendations:

*   **Prefer Newer Targets for New Development:** If **you maintain** the library’s code (or have the ability to fork/rebuild it), strongly consider upgrading its target. Microsoft _recommends retargeting .NET Standard 1.x libraries to .NET Standard 2.0 or directly to a modern .NET version (like net8.0)_[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20your%20project%20targets%20,x%20targets). Targeting .NET Standard 2.0 is often a safe bet because it dramatically expands the available API surface while still supporting older platforms (including .NET Framework 4.6.1+)[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20you%27re%20building%20reusable%20libraries,a%20minimal%20increase%20in%20reach). In many cases, jumping all the way to a **.NET 8** target can be ideal if you no longer need to support anything older than .NET 8 – this lets you use the latest runtime features and C# versions in the library. The general guidance is: _“We don't recommend targeting .NET Standard 1.x, as you'd limit the available feature set for a minimal increase in reach.”_[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20you%27re%20building%20reusable%20libraries,a%20minimal%20increase%20in%20reach). So for any actively developed library, move it forward if possible.
    
*   **Multi-Target for Broad Compatibility:** If you need to maintain broad compatibility (for example, your library is used in some .NET Framework 4.x projects as well as .NET 8), you can **multi-target** the project. Many NuGet packages choose to target both **`netstandard2.0`** (to cover .NET Framework and older .NET Core) and **`net5.0`/`net6.0`+** (to light up new features) in one package. Microsoft notes that most widely-used libraries do exactly this: _support .NET Standard 2.0 for maximal reach, and add a .NET 5+ target to leverage latest features on newer runtimes_[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20you%20don%27t%20need%20to,NET%205). You could similarly multi-target `netstandard1.3` and `net8.0`, but since .NET Standard 2.0 supersedes 1.3 with almost the same reach, it’s usually better to target 2.0 instead of 1.3 for the “common denominator” target. In summary, consider delivering an updated version of the library that at least targets .NET Standard 2.0 (if not higher) alongside your .NET 8 code. This way, your .NET 8 project can take a dependency on a more up-to-date library build (eliminating the need for all those 1.x compatibility shims and giving you more API to work with internally).
    
*   **Check for Upgraded Versions:** If the .NET Standard 1.3 library is a third-party or legacy NuGet package that you consume, search to see if a newer version of that library exists. Many projects that started on .NET Standard 1.x have released updates targeting .NET Standard 2.0 or .NET 6/7/8 as the ecosystem evolved. Upgrading to a later version of the package can resolve compatibility quirks and improve performance. It can also get rid of any build warnings about older targets. For example, some libraries initially targeting .NET Standard 1.3 (for maximum reach at the time) later added .NET 6/7 support once those became widely adopted (often indicated on NuGet as “netstandard1.3; net6.0; net7.0” targets, etc.)[github.com](https://github.com/GregFinzer/Compare-Net-Objects/blob/master/Readme.md#:~:text=NET%20Framework%204,Android)[nuget.org](https://www.nuget.org/packages/comparenetobjects/#:~:text=,4). Always prefer the latest compatible version of a library for a .NET 8 project, as it’s likely been tested with .NET Core/5+ environments.
    
*   **Test the Integrated Library:** After adding the .NET Standard 1.3 library to your .NET 8 project, **run your tests** or exercise the library’s functionality thoroughly. Although no compile-time issues are expected, runtime testing can reveal any subtle differences (for example, maybe the library performs reflection or file access that behaves differently on .NET 8, etc.). Pay attention to any console or log warnings that .NET might emit about deprecated APIs when the app runs. In general, if the library is purely computation or business logic, it should behave the same. But if it deals with resource loading, configuration, or other runtime interactions, validate those in the new environment.
    
*   **Monitor .NET 8 Specific Warnings/Errors:** If you compile the library from source against .NET 8 (or if your solution includes the library project targeting net8.0), you might encounter **compiler warnings** for outdated patterns. For instance, async code may show analyzers suggestions, or using certain older .NET idioms might trigger warnings under the latest SDK. Addressing these (if you have access to the code) can make the library more robust. Even if you’re just consuming a binary, Visual Studio may show you an analyzer warning if the library uses something like `BinaryFormatter` or other deprecated component – these are cues to be aware of potential issues. (For example, if a .NET Standard 1.3 library internally uses an API that’s obsolete, you might see an MSBuild warning or runtime advisory about it.)
    
*   **Maintain a Unified Target Platform if Possible:** When developing your application, it’s simpler if all projects use modern targets. If you have the option to update the class library (or find an updated fork), doing so will let you keep your entire solution on a uniform, supported target (e.g., everything on .NET 8). This avoids the mental overhead of mixing old and new targets. However, if the .NET Standard 1.3 library is from a third party and cannot be changed, rest assured that referencing it is supported. Just consider isolating it if needed, and plan long-term to replace or update it if the opportunity arises (since .NET Standard 1.x is essentially _frozen_ and not recommended for new work[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/standard/net-standard#:~:text=If%20you%27re%20building%20reusable%20libraries,a%20minimal%20increase%20in%20reach)).
    

Specific API Considerations in .NET 8
-------------------------------------

Most of the APIs in .NET Standard 1.3 are basic functionalities that continue to work in .NET 8. However, it’s worth highlighting a few **specific APIs/patterns** that could pose issues or deserve attention:

*   **BinaryFormatter and Legacy Serialization:** Although .NET Standard 1.3 itself did _not_ include `BinaryFormatter` (it was added in .NET Standard 2.0), some older libraries might use binary serialization or similar techniques via conditional compilation. In .NET 8, `BinaryFormatter` is **fully obsolete and even disabled** in many scenarios due to security concerns. For example, a developer reported that a .NET Standard library using BinaryFormatter ran into runtime exceptions on .NET 8 – the app crashed on .NET 8 because _“the binary formatter serialization and deserialization are disabled”_ by default for security[stackoverflow.com](https://stackoverflow.com/questions/78267859/does-net-8-really-support-net-standard-2-0-binaryformatter-issue#:~:text=I%20also%20have%20an%20app,8.0). This illustrates that **support doesn’t always mean identical behavior**: .NET 8 _includes_ the BinaryFormatter API for compatibility (fulfilling .NET Standard 2.0), but actually using it will trigger errors unless explicitly re-enabled. **Recommendation:** If an older library uses `BinaryFormatter` or similar deprecated serialization, you should update that part of the code (e.g., switch to `System.Text.Json` or `XmlSerializer`) or ensure the feature is turned off, because .NET 7/8 actively blocks BinaryFormatter usage by default[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/serialization/5.0/binaryformatter-serialization-obsolete#:~:text=Due%20to%20security%20vulnerabilities%20,enabled%20%203%20functionality).
    
*   **Cryptography APIs:** As mentioned, certain crypto primitives from early .NET are present but deprecated. .NET 8 marked the old `RSA.EncryptValue` and `RSA.DecryptValue` methods as obsolete (and they were removed from the public contract in .NET 7+)[learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/core/compatibility/8.0#:~:text=RSA,incompatible%20Preview%201). These methods aren’t commonly used (they were low-level hooks usually not needed with RSA), but if a .NET Standard 1.3 library somehow relies on them, it would not compile against .NET 8 and could fail at runtime if it tries to invoke them via reflection. The broader RSA API and other cryptography functions (like SHA hashing, AES, etc.) continue to work, but developers should use the newer recommended patterns. Similarly, older SSL/TLS configurations or algorithms considered insecure may be disabled by default in .NET 8’s networking stack. If your library dealt with things like TLS 1.0/1.1, be aware that .NET 8 (and even 6/7) may require TLS 1.2+ by default in many contexts.
    
*   **Networking and HTTP:** .NET Standard 1.3 libraries might use `HttpClient` (which is fully supported in .NET 8) or possibly `WebRequest/WebClient`. The latter (WebRequest) is deprecated in .NET 6+; it’s still functional, but on .NET 8 it will log warnings that it’s not the recommended API. Functionally, a library using WebRequest should still work (the compatibility shims are there), but performance may not be optimal. If you maintain the lib, port it to HttpClient for better support. If you just use it, there’s no breaking issue – just something to note if you see deprecation messages.
    
*   **Threading and Sync Context:** .NET Standard 1.3 supports basic threading/tasks, and those behave the same in .NET 8. One change in .NET 8 (and .NET 6) is improvements to the thread pool and synchronization contexts, but that should _improve_ performance or deadlock avoidance for libraries using `Task` and `async/await`. No action needed, but if your library had custom Task scheduling, just be aware of any subtle differences.
    
*   **Reflection and Emission:** Most reflection APIs from .NET Standard 1.3 (Type inspection, MethodInfo.Invoke, etc.) are fully available. .NET 8 does have the “trimming” and ahead-of-time compile features which can affect reflection (e.g., if you publish with trimming, reflection heavy libraries might need extra config). But in a normal .NET 8 app, reflection works as usual. If the library uses `Assembly.Load(byte[])` or dynamic code gen (`System.Reflection.Emit`), those are also supported on core (with the exception of some contexts like Native AOT). There’s no outright removal here, but something to keep in mind if deploying to an AOT scenario.
    
*   **Platform Invokes (P/Invoke):** If the .NET Standard 1.3 library uses P/Invoke to call native code, it should still work on .NET 8 _provided_ the native dependency is available. .NET 8’s interop is compatible with how .NET Core has always done it. Just ensure any native libraries are present for the OS you run on (Windows vs Linux, etc.). Nothing specific in .NET 8 breaks P/Invokes from .NET Standard libs.
    

In summary, **nearly all APIs from .NET Standard 1.3 function correctly in .NET 8**, but you should be alert to those that .NET 8 has marked as obsolete or changed for security/performance. Reading through the _.NET 8 breaking changes_ documentation (especially for core libraries) can be useful if your older library does something unusual. The good news is that common functionality (collections, LINQ, IO, networking, threading, etc.) was carried forward with full compatibility. The .NET team has been careful to keep the promise that “if it was in .NET Standard, it’ll continue to exist in .NET 5+” – with only a few exceptions where they _soft-removed_ things by obsoleting them.

In conclusion, **.NET 8 has excellent backward compatibility** and will happily run .NET Standard 1.3 libraries. Whenever feasible, modernize the libraries to target newer frameworks – not because .NET 8 can’t run them, but because it will make your life easier and your code more powerful. By following the above practices, you can confidently use older .NET Standard 1.3 assets in new .NET 8 applications while minimizing technical debt and future-proofing your projects.
